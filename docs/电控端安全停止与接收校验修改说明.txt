电控端代码修改说明：接收有效性、通信失效与安全停止
============================================================
日期：2026-11-02
对象：电控固件维护人员、视觉联调人员
性质：基于当前源码核对的修改需求与验收说明，不是已验证的固件补丁。

一、先看结论
------------------------------------------------------------
本次不能只修改 USB 数据接收。需要核对并修复以下完整链路：

  数据接收有效性 → 通信新鲜度 → 模式转换 → 最终停止输出

已经确认的主要问题：
1. 接收数据先被复制到控制变量，随后才计算 CRC，而且 CRC 结果没有阻止控制使用。
2. 接收处理没有依据本次实际接收长度和新数据事件区分完整消息、旧缓冲区。
3. 已有“目标丢失 1 秒”逻辑不是通信超时；旧命令可不断刷新目标计时。
4. AUTO 模式缺少 Prepare1 状态处理，撤销开火后可能保留上一轮电机输出。

第 4 项意味着：即使加了通信超时，并把视觉 mode 设为 0，也不能据此认定已经停机。
必须一直检查到最终电机指令，不能仅检查某个状态变量。

本说明仅针对异常数据拒绝、失联保护和停止行为。
不涉及提高射击性能、修改瞄准算法、弹道参数、发射频率或云台 PID。

三、问题 A：CRC 没有形成接收有效性保护
------------------------------------------------------------
位置：
  Task/Src/Auto_aim.c
  Auto_aim_Task()：第 63～68 行
  usb_recieve()：第 71～79 行

当前行为：
  usb_recieve() 先按首字节检查缓冲区，然后 memcpy 到 Gimbol_Shoot。
  Auto_aim_Task() 随后计算 crc_ok。
  在本次检查的应用代码中，crc_ok 没有被用于阻止控制消费无效消息。

为什么有问题：
  校验结果仅被保存，不等于校验保护生效。
  一旦无效数据先进入共享控制变量，后续消费者可能已经使用这些数据。

修改要求：
  A1. 无效、不完整或校验失败的消息不得进入可供控制使用的状态。
  A2. 失败消息不能刷新“最后一次有效通信”的时间。
  A3. 接收失败原因应可观察，以便区分通信问题与软件状态问题。
  A4. 不得以“数据首字节正确”替代完整性与有效性检查。

验收关注点：
  输入无效消息后，控制状态不被污染，通信有效期不被延长。
  不能只看到 crc_ok 为 0 就判定通过，还要检查消费者实际读取的状态。

四、问题 B：接收回调和旧缓冲区被混用
------------------------------------------------------------
位置：
  Src/usbd_cdc_if.c：CDC_Receive_FS()，第 261～268 行
  Task/Src/Auto_aim.c：usb_recieve()，第 71～79 行

当前行为：
  CDC_Receive_FS() 仅重新设置接收缓冲区并继续接收。
  usb_recieve() 从任务循环主动调用该回调，再检查缓冲区并固定长度复制。
  处理过程没有使用本次真实接收长度，也没有记录是否发生了新的有效接收。

为什么有问题：
  缓冲区中“有字节”不代表刚刚收到了一条完整的新消息。
  上次的数据可能仍在缓冲区中；一次回调的数据边界也不能直接当作应用消息边界。
  任务循环次数和有效接收次数是两回事。

修改要求：
  B1. 明确真实接收事件与应用处理的边界，不再把轮询旧缓冲区当成新消息。
  B2. 完整性判断必须基于实际收到的数据，不得用缓冲区容量替代消息长度。
  B3. 不完整、重复消费或无效数据不能制造“通信仍正常”的假象。
  B4. 回调与任务共享状态时，消费者不能读到一次更新到一半的状态。
  B5. 由固件维护人员按现有 USB 栈和 RTOS 结构落实，不直接粘贴未经验证的示例。

说明：
  先前聊天中的短示例没有覆盖完整的接收生命周期与并发一致性，不能作为交付补丁。

五、问题 C：目标丢失计时不能代替通信超时
------------------------------------------------------------
位置：
  Task/Src/GimbolControl.c：Gimbol_AUTO()，第 54～67 行

当前行为：
  target_valid 由保存在 Gimbol_Shoot 中的 mode 判断。
  只要旧 mode 仍被视为有效，每个控制循环就更新 last_target_time。
  现有 1 秒逻辑只有在目标状态变为无效后，才可能进入对应的等待分支。

为什么有问题：
  “视觉仍在通信，但报告没有目标”和“视觉已经断线”是不同事件。
  通信断开时，旧 mode 未改变，目标计时仍可能被不断刷新。
  当前逻辑没有证明收到新消息，因此不能检测该类失联。

修改要求：
  C1. 通信新鲜度必须来自真实的有效接收事件。
  C2. 超出允许的有效通信时间后，应撤销相应的视觉控制与发射许可。
  C3. 未收到首个有效消息、连接中断、重连后的旧状态，都应有明确处理。
  C4. 通信恢复不应因残留状态意外恢复此前的危险输出；恢复策略需明确验收。
  C5. 失效条件必须传播到模式层和输出层，不能只修改一个标志位。

超时数值说明：
  先前提到的 50 ms 没有经过实测确认，不是本说明的验收定值。
  发送线程的标称周期不能保证实际消息按同样间隔到达。
  具体界限应由负责人结合实测时序与允许的停止响应要求确定，并记录依据。
  实际停止响应还受到任务调度、输出传输和机械响应影响。

六、问题 D：AUTO 的 Prepare1 分支遗漏，旧输出可能继续发送
------------------------------------------------------------
位置：
  Task/Src/ModeControl.c：第 42～44 行
  Task/Src/Shoot.c：ShootControl() 的 AUTO 分支，第 187～267 行
  Task/Src/Shoot.c：ShootTask()，第 16～23 行

当前代码链路：
  1. AUTO 模式下，发射拨杆居中。
  2. 视觉 mode 不再是开火状态时，Mode_Control() 设置 ShootMode = Prepare1。
  3. ShootControl() 的 AUTO 分支没有处理 Prepare1，也没有兜底撤销旧输出。
  4. ShootTask() 随后仍调用输出发送函数。

直接后果：
  即使新的停止意图已经到达，旧的 ShootMotor[].Motorout 也可能继续被发送。
  这是输出状态处理问题，单独增加 CRC 或接收超时不能解决。

已完成的主机隔离复现：
  测试前将三路 Motorout 预置为 111、222、333，仅用于模拟残留非零输出。
  不调用真实硬件，不启动发射流程。

  状态                 原函数执行结果
  AUTO + Prepare1      三路仍为 111、222、333
  RC + Prepare1        拨弹输出变为 0；摩擦轮按准备状态处理
  STOP                 在模拟 PID 条件下，三路输出为 0

  复现记录：/tmp/bof-stop-path-audit-8wjdce7b/result.txt
  临时目录可能被系统清理；上述结果已在本说明保留。

修改要求：
  D1. 所有撤销发射的状态都必须定义最终输出，不能隐式沿用上次输出。
  D2. AUTO 与 RC 的停止语义需逐一核对，不能假定两者分支相同。
  D3. 未知或未处理状态应进入经确认的安全处理路径。
  D4. 验收应检查最终发给执行器的指令，而不只是 ShootMode 或 mode 的值。
  D5. 不应简单认为“写零电流”和“机械停止”等价；由电控确认适合设备的停止行为。

七、必须明确区分的三种停止
------------------------------------------------------------
1. 停止发射：撤销发射动作，但不必然意味着云台停止运动或摩擦轮停止。
2. 退出视觉控制：可能回到遥控或扫描，不等于整机静止。
3. 整机安全停止：各执行器进入明确的安全状态，并具备适当的独立停止手段。

当前 mode 0 不能直接等同于第 3 种状态。
现有 s[0] 下挡对应软件 STOP，但依赖遥控数据被接收、任务运行和输出链路正常。
本次没有验证遥控失联保护，不能把软件拨杆 STOP 当作独立硬件急停的证明。

电控交付说明应明确：
  - 通信失效后，各执行器分别进入什么状态。
  - 哪些状态撤销发射，哪些状态撤销视觉控制。
  - 停止条件在各任务之间如何保持一致。
  - 通信恢复后是否需要操作员确认，避免旧状态意外恢复。

九、验收项目：先在断能或隔离环境中证明停止行为
------------------------------------------------------------
以下是安全保护验收要求，不是装弹或射击测试步骤。
优先使用主机替身、硬件在环的隔离输出或执行器断能环境。

项目 1：未建立有效通信
  预期：不存在从未初始化或历史状态继承的有效控制许可。

项目 2：无效或不完整输入
  预期：不污染控制状态，不刷新有效通信时间。

项目 3：停止接收、连接中断或发送程序退出
  预期：按已确定的界限进入失效状态，最终输出符合安全定义。
  记录：最后有效接收、失效判断、模式变化、最终输出变化的时刻。

项目 4：AUTO 撤销发射
  预期：进入非发射状态后，最终输出不保留先前的发射输出。
  特别覆盖 Prepare1 路径，以及 RC 与 AUTO 两种模式。

项目 5：重新建立通信
  预期：不因残留旧状态自动恢复危险输出，符合已确定的恢复策略。

项目 6：软件 STOP 与独立停止手段
  预期：分别确认其作用范围和依赖条件，不将两者混为一谈。

每项记录：
  固件版本、测试环境、初始状态、触发条件、最终输出、观察结果、是否通过。

只有状态变量变化、日志打印成功或视觉程序正常退出，均不足以单独判定通过。
